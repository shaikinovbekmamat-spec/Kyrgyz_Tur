# Kyrgyz Tur

Django-сайт туров по Кыргызстану: каталог, фильтры, регистрация, личный кабинет,
заявки без онлайн-оплаты и управление через Django Admin.

Пошаговая подготовка к Vercel: [DEPLOY_VERCEL.md](DEPLOY_VERCEL.md).

## Запуск

Нужен Python, совместимый с Django 6.1 (3.12 или новее).

```powershell
python -m venv .venv
.venv/Scripts/python.exe -m pip install -r requirements.txt
Copy-Item .env.example .env
# Впишите параметры PostgreSQL и пароль в .env.
# Создайте пустую базу kyrgyz_tur через pgAdmin (Databases → Create → Database).
.venv/Scripts/python.exe manage.py migrate
.venv/Scripts/python.exe manage.py createsuperuser
.venv/Scripts/python.exe manage.py runserver
```

Проект использует PostgreSQL. Параметры подключения находятся в `.env`, который
не включается в Git. Переменные окружения имеют приоритет над значениями файла.
PostgreSQL должен быть запущен; пользователь должен иметь доступ к указанной базе.
Для `manage.py test` требуется право создания тестовой базы.

## Перенос старой SQLite-базы

Остановите сайт на время переноса. Сохраните копию `db.sqlite3`. Экспортируйте
данные старой базы, затем примените миграции и импортируйте их в **пустую**
PostgreSQL-базу, до создания суперпользователя и демонстрационных туров:

```powershell
New-Item -ItemType Directory -Force backups
Copy-Item db.sqlite3 backups/db.sqlite3
.venv/Scripts/python.exe manage.py dumpdata --settings=Kyrgyz_Tur.sqlite_settings --natural-foreign --natural-primary --exclude contenttypes --exclude auth.permission --exclude sessions --exclude admin.logentry --output backups/sqlite-data.json
.venv/Scripts/python.exe manage.py migrate
.venv/Scripts/python.exe manage.py loaddata backups/sqlite-data.json
.venv/Scripts/python.exe manage.py check
```

Экспорт содержит учётные записи и хеши паролей. Не публикуйте каталог `backups`.
Фотографии остаются в каталоге `media`, их также нужно сохранять при переносе.
Исходная SQLite-база сохраняется; основной сайт больше её не использует.

Откройте http://127.0.0.1:8000/. В `/admin/` добавьте регионы, категории и туры;
внутри тура — фотографии и будущие даты со свободными местами.
Демонстрационные туры можно создать командой `python manage.py seed_demo`.

Пользователь выбирает дату и количество участников. Ожидающая заявка не резервирует
места. В админке выберите заявки и действие «Подтвердить выбранные бронирования».
Система повторно проверяет дату и места, списывает их атомарно. Повторное
подтверждение не списывает места; отмена возвращает их только один раз.
Статус, число участников и дата в существующей заявке доступны только для чтения.
Завершить подтверждённые поездки после их окончания можно отдельным действием.

Подбор ограничивает бюджет на человека и длительность, проверяет стоимость
будущих дат с местами и сортирует по доле совпавших интересов, затем по цене.
Для «горы», «озёра», «культура» используются группы родственных ключевых слов.
Это подбор по словам, а не обработка произвольной фразы с извлечением бюджета.

```powershell
python manage.py check
python manage.py test
```

Настройки рассчитаны на локальную разработку. Для размещения задайте секретный
ключ через окружение, отключите DEBUG и настройте ALLOWED_HOSTS и обслуживание
статических файлов и фотографий.
# Урок 19: почта, кеш и языки

Регистрация доступна в `/accounts/register/`, вход — в `/accounts/login/`.
Переключатель в шапке меняет язык интерфейса между русским и английским.
Контент из базы (названия и описания туров, комментарии) автоматически не переводится.
Переводы хранятся в `locale/en/LC_MESSAGES/django.po`; скомпилированный `django.mo`
включён в проект. После изменения переводов выполните `python manage.py compilemessages`
в окружении с установленным GNU gettext.

После нового комментария на сайте отправляется письмо на `COMMENT_NOTIFICATION_EMAIL`.
По умолчанию письмо выводится в консоль сервера. Для реальной доставки скопируйте
почтовые параметры из `.env.example` в `.env`, задайте
`EMAIL_BACKEND=django.core.mail.backends.smtp.EmailBackend`, адрес SMTP-сервера,
порт, логин, пароль, адрес отправителя и получателя. Настройка рассчитана на STARTTLS
(обычно порт 587). Перезапустите сервер после изменения `.env`.
Ошибка SMTP записывается в журнал и не отменяет комментарий; автоматического повтора отправки нет.

Содержимое каталога кешируется на 60 секунд отдельно для каждого языка и набора
параметров URL. Навигация, личные страницы, сообщения, CSRF-токены и комментарии
не кешируются. Изменения туров появляются в каталоге в течение минуты.
Используется локальный кеш процесса; после перезапуска он очищается.

## Тесты и покрытие

Установка зависимостей для разработки и запуск всех тестов:

```powershell
.venv/Scripts/python.exe -m pip install -r requirements-dev.txt
.venv/Scripts/python.exe manage.py test --settings=Kyrgyz_Tur.test_settings
```

`test_settings` использует отдельную SQLite-базу в памяти, локальный кеш,
почтовый backend в памяти и быстрый хешер паролей только для тестов.
Рабочая база не изменяется, PostgreSQL и SMTP для этого запуска не нужны.

Измерение покрытия, включая ветвления, и HTML-отчёт:

```powershell
.venv/Scripts/python.exe -m coverage run manage.py test --settings=Kyrgyz_Tur.test_settings
.venv/Scripts/python.exe -m coverage report
.venv/Scripts/python.exe -m coverage html
```

Отчёт открывается из `htmlcov/index.html`. В `.coveragerc` задан порог 95%:
`coverage report` завершится с ошибкой при меньшем покрытии. Из измерения исключены
сами тесты и миграции; учитывается код приложений `tours`, `bookings`, `users`.

Набор проверяет каталог, поиск, фильтры и пагинацию, рекомендации и границы бюджета,
валидацию моделей и форм, регистрацию и вход, права доступа, создание и отмену
бронирований, учёт мест, профиль, административные действия, отзывы, комментарии,
почту, кеш и переключение языка. Общие данные для новых тестов находятся в
`tours/test_helpers.py`; кеш очищается между этими тестами.

Для проверки на PostgreSQL с параметрами из `.env`:

```powershell
.venv/Scripts/python.exe manage.py test
```

Пользователю PostgreSQL требуется право создания тестовой базы. SQLite-прогон
не проверяет поведение блокировок PostgreSQL при одновременных транзакциях;
тесты повторного подтверждения проверяют последовательные обращения и устаревшие
экземпляры моделей, а не параллельные запросы.
